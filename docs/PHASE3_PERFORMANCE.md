# Phase 3 Docs Performance

Phase 3 adds a reproducible Docs semantic benchmark and a full native-application memory smoke.

The numbers below are GitHub-hosted Ubuntu trend evidence from commit `848df4f9`. They are not substitutes for repeated Windows/macOS/Linux reference-machine measurements.

## Exact 20-page fixture

The fixture is generated by Nexa itself and CI rejects it unless the paginator produces exactly 20 pages.

It contains:

- 20 explicit page groups;
- 240 semantic paragraphs including table-cell paragraphs;
- Latin and CJK text;
- mixed run formatting;
- list references;
- 2×3 tables on each page;
- edit/search/save/reopen validation.

Snapshot:

| Metric | Result |
| --- | ---: |
| Requested pages | 20 |
| Laid-out pages | 20 |
| Paragraphs | 240 |
| Estimated semantic model bytes | 123,160 |
| Initial DOCX size | 3,410 bytes |
| Edited DOCX size | 3,417 bytes |
| Search matches | 121 |

The generated DOCX is intentionally compressible. File size is not intended to model media-heavy documents; memory and package stress for large opaque Parts are covered separately by the Phase 2 OOXML benchmark.

## Docs semantic benchmark

Release-mode result on the shared Ubuntu runner:

| Operation | Result |
| --- | ---: |
| Build semantic fixture | 120 µs |
| Paginate 20 pages | 65 µs |
| Initial DOCX save | 591 µs |
| DOCX reopen | 483 µs |
| Edit + search operation | 155 µs |
| Edited DOCX save | 375 µs |
| Verification reopen | 411 µs |
| Complete benchmark peak RSS | 3,876 KiB (~3.8 MiB) |

Current shared-runner regression ceilings are deliberately wider than the measured result:

- semantic benchmark peak RSS <= 32 MiB;
- pagination <= 100 ms;
- edit/search <= 50 ms;
- reopen <= 250 ms;
- edited save <= 500 ms.

These are CI gross-regression limits, not claims about end-user interaction latency.

## Full Nexa Office with 20-page DOCX open

The same generated DOCX is passed to the real release `nexa-office` binary. The process settles for 30 seconds before memory is sampled, followed by a 10-second idle-CPU sample.

| Metric | Result |
| --- | ---: |
| Release executable | 15,600,712 bytes (~14.9 MiB) |
| RSS | 20,796 KiB (~20.3 MiB) |
| PSS | 15,920 KiB (~15.5 MiB) |
| Private memory | 13,776 KiB (~13.5 MiB) |
| Idle CPU | 0.000% of one logical core |

The shared-runner Docs application smoke enforces private memory <= 100 MiB. The product target in [PERFORMANCE.md](PERFORMANCE.md) remains <= 100 MiB for a typical 20-page DOCX, with a 150 MiB hard budget.

This result is comfortably below the target in this synthetic fixture, but it is still shared-runner trend evidence. Media-heavy documents, complex typography and final page rendering will require additional reference-machine measurements as fidelity grows.

## Start-screen regression check

On the same Phase 3 branch, the native start-screen smoke measured approximately:

- PSS: 15,024 KiB (~14.7 MiB);
- private memory: 12,884 KiB (~12.6 MiB);
- idle CPU: 0.000%;
- release executable: 15,600,712 bytes.

Linking the Docs engine increased the release binary from the Phase 1 shell baseline, but the native start-screen memory remains far below the 60 MiB hard shell budget.

## Interpretation

The important architecture result is not the microsecond-scale synthetic timing by itself. It is that:

- the start screen remains lightweight after linking Docs;
- opening the exact 20-page semantic fixture does not cause memory to scale catastrophically;
- editor history is bounded;
- pagination works without page raster caches;
- unsupported content is blocked from destructive save rather than traded for speed.

Performance gates must tighten or evolve as the renderer, text shaper and richer real-world corpus are added.
